import NewsletterForm from '@/components/react/NewsletterForm';

The newsletter form appears in the footer of every page, after each blog post and on
[/newsletter](/newsletter). It asks for an address only. Submitting it stores the address as
_pending_ and sends one email with a confirmation link; nothing else is sent until that link is
opened. Every newsletter then carries an unsubscribe link that ends the subscription with one
click on a confirmation page.

  </p>
</Callout>

## The flow

<Steps>

1. **Request.** `NewsletterForm.tsx` posts the address to the `newsletter.subscribe` action. The
   action applies the same protections as the contact form: a honeypot field, per-address and
   per-IP throttles in the `throttle` table, and Zod validation.
2. **Store, then send.** `subscribeToNewsletter()` in `src/lib/newsletter.ts` inserts a
   `pending` row in `newsletter_subscriber` with a random 256-bit token and emails the
   confirmation link. A second request for a pending address issues a new token, which retires
   the earlier email; a request for a confirmed address sends an "already subscribed" email
   with the unsubscribe link instead. The visitor sees the same message in every case, so the
   form cannot be used to find out who is subscribed.
3. **Confirm.** Opening `/newsletter/confirm?token=…` marks the row `confirmed`, records the
   time and, when `RESEND_AUDIENCE_ID` is set, adds the address to the Resend segment. A link
   works for seven days; after that the page asks the visitor to request a new one.
4. **Unsubscribe.** `/newsletter/unsubscribe?token=…` shows the address and a button. The
   button posts the `newsletter.unsubscribe` action; opening the link alone changes nothing,
   because mail clients and security scanners fetch links from emails. The audience is updated
   and an old confirmation link can no longer revive the subscription.

</Steps>

The token is the only secret, it lives in the recipient's inbox, and it can do exactly two
things: confirm or end its own subscription. It is stored as is, like Better Auth's verification
tokens, so the CSV export can include an unsubscribe link for each address.

## Props

| Prop        | Type                                                        | Default  |
| ----------- | ----------------------------------------------------------- | -------- |
| `source`    | `'footer' \| 'blog' \| 'page' \| 'docs'`                    | `'page'` |
| `compact`   | `boolean`, input and button on one row                      | `false`  |
| `className` | extra classes for the `<form>`                              | –        |
| `labels`    | `Partial<NewsletterFormLabels>`, strings for another locale | English  |

`source` is stored with the subscription and shown on the admin page; it says where people
subscribe, nothing more.

## Without JavaScript

The island's form has a real `action`: `/newsletter?_action=newsletter.subscribe`. Without
JavaScript the browser posts there, the on-demand `/newsletter` page runs the action through
`Astro.getActionResult()`, redirects to `/newsletter?sent=1` on success and renders the
validation or delivery error above the form otherwise. This is the plain-form pattern from the
[actions guide](/docs/guides/actions-and-forms#progressive-enhancement), used for a form that
sits on static pages. The confirm and unsubscribe pages are server rendered and need no
JavaScript at all.

## Sending a newsletter

The template stores subscribers; it does not send newsletters. Two ways to do that:

- **Resend segment.** Create a segment in Resend (**Contacts → Segments**; older dashboards
  call them audiences), copy its ID into `RESEND_AUDIENCE_ID` next to a full-access
  `RESEND_API_KEY`, and confirmed addresses are created as contacts in it; unsubscribing here
  marks the contact unsubscribed there. Write and send from Resend's broadcasts, whose footer
  includes Resend's own unsubscribe link. The admin page shows an **Audience** column with the
  addresses the provider has not received yet, for example because the API was unavailable;
  the next change to that address retries.

  To make Resend's unsubscribe link count here as well, add a webhook in Resend
  (**Webhooks → Add**) with the URL `https://<your site>/api/newsletter/webhook` and the
  `contact.updated` and `contact.deleted` events, and put its signing secret (it starts with
  `whsec_`) in `RESEND_WEBHOOK_SECRET`. The endpoint verifies every delivery's signature and
  timestamp (`src/lib/webhook-signature.ts`), marks the address unsubscribed and records it in
  the audit log. It only ever opts people out: a contact re-subscribed at Resend still has to
  confirm through the form. Without the secret the endpoint answers 404, and the admin
  overview says so.

- **CSV export.** The **Download confirmed (CSV)** button on `/admin/subscribers` posts to
  `/admin/subscribers.csv` (a GET answers 405, so a prefetched link cannot record a download) and produces
  `email,confirmed_at,unsubscribe_url`. Whatever tool sends the newsletter must put each
  address's `unsubscribe_url` in the footer. Each download is recorded in the audit log.

## Data and retention

| Status         | Meaning                                        | Kept                                         |
| -------------- | ---------------------------------------------- | -------------------------------------------- |
| `pending`      | Requested, confirmation not opened yet         | `NEWSLETTER_RETENTION_DAYS` (default 7)      |
| `confirmed`    | Receives email                                 | Until unsubscribed or removed by an admin    |
| `unsubscribed` | Opted out; the address is no longer written to | `NEWSLETTER_RETENTION_DAYS` after opting out |

`pnpm db:prune` (the weekly **Prune data** workflow) deletes the rows in the last column, so an
address that never confirmed or that opted out disappears from the database within days. The
subscription is tied to the address, not to an account: it appears in a signed-in user's data
export when the address is verified, and it is not removed with the account, because the
consent was given separately and ends through the unsubscribe link. Administrators can remove
any row from `/admin/subscribers`, for requests that arrive by other means.

## Turning it off

Set `newsletter.enabled` to `false` in `src/site.config.ts`. The footer block, the blog card,
the palette entry and `/newsletter` disappear; the confirm and unsubscribe pages keep working
so existing links in inboxes still do what they say. A form you place yourself should check the
same flag:

```astro
{siteConfig.newsletter.enabled && <NewsletterForm client:visible source="page" />}
```

## Accessibility

The email field has a visually hidden label, the error is announced through `role="alert"` and
referenced with `aria-describedby`, and the success message is a status region. The unsubscribe
page names the address it is about and uses a real button for the change. The axe scan in
`tests/e2e/a11y.spec.ts` covers `/newsletter`, the confirmation and unsubscribe pages and the
subscriber list in the admin area.

- `tests/e2e/newsletter.spec.ts` subscribes from the footer, reads the token from the test

  path through `/newsletter` and a signed webhook delivery that ends a subscription.
