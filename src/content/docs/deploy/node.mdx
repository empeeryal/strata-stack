The Node target produces a self-contained server in `dist/server/entry.mjs` that serves static
files and on-demand routes from one process. It is the default target and the one used by the
end-to-end tests. A request with a trailing slash (`/about/`) is answered with a 301 to the
page's one address (`/about`), see [SEO](/docs/guides/seo#one-address-per-page).

## Build and run

```bash
pnpm build:node
HOST=0.0.0.0 PORT=4321 pnpm start
```

`pnpm start` sets `NODE_ENV=production`, which turns on the production rules: the secret and the
public URL are checked at the first request, and email is never written to the console. To look
at a production build locally without those rules, run `node ./dist/server/entry.mjs` directly.
The server reads configuration from the process environment only; nothing is loaded from `.env`
at runtime. Provide `DATABASE_URL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL` and `SITE_URL` (at
build time) through your platform.

## Docker

The multi-stage `Dockerfile` installs dependencies with pnpm, builds the site, then copies the
build output, the migrations and the production dependencies into a `node:24-slim` image running
as the unprivileged `node` user, with a health check against `/api/health`. `tini` runs as PID 1
and forwards signals, so `docker stop` ends the server at once instead of after the kill timeout.

```bash
docker build --build-arg SITE_URL=https://example.com -t strata-stack .
docker run -p 4321:4321 --env-file .env strata-stack
```

`docker-compose.yml` adds a named volume at `/app/.data` so a `file:` database survives
restarts. For production prefer Turso or another hosted libSQL/SQLite service so the database is
not tied to one container.

Run migrations before starting a new version. The image ships `scripts/migrate.ts`, which
applies the SQL files in `drizzle/` with Drizzle's migrator and needs no dev dependencies:

```bash
docker run --rm --env-file .env strata-stack node scripts/migrate.ts
```

Without a container, the **Migrate database** GitHub Actions workflow applies the same migrations
to a Turso database; see [CI and releases](/docs/guides/ci-cd#database-migrations).

## Reverse proxy

Put the server behind a TLS-terminating proxy (Caddy, nginx, a platform load balancer). The
proxy should also compress responses: the Node server sends HTML, CSS and scripts as they are,
and compression is what keeps the mobile Lighthouse scores where the CI budgets expect them
(Caddy does it by default; nginx needs `gzip on`). The server sends the security headers itself,
for server-rendered responses through the middleware and for prerendered pages through the
header map the build writes (`integrations/security-headers.ts`); the proxy only needs to pass
them through. The Node adapter applies that map to pages only: static assets (`/_astro/*`, the
icons, `robots.txt`, the feeds) leave the Node server without the extra headers, so add the same
set at the proxy for everything that is not a page (Caddy's `header` directive, nginx
`add_header`). Make sure the proxy forwards the original
`Host`, plus `X-Forwarded-For` and `X-Forwarded-Proto`: Astro only trusts those headers when
`Host` is the site's own hostname (`security.allowedDomains`, filled in from the site URL by
`config/trusted-hosts.ts`), and without them every visitor would share the proxy's address for
rate limiting.

The proxy must **set** `X-Forwarded-For` to the connecting address, not append to a value the
visitor sent: Astro reads the first address in the header, so an appended header lets anyone
pick their own rate-limit key by sending `X-Forwarded-For` themselves. Caddy does the right
thing by default (it drops forwarded headers from clients that are not in `trusted_proxies`).
With nginx use `$remote_addr`, not the common `$proxy_add_x_forwarded_for`:

```nginx
location / {
  proxy_pass http://127.0.0.1:4321;
  proxy_set_header Host $host;
  proxy_set_header X-Forwarded-For $remote_addr;
  proxy_set_header X-Forwarded-Proto $scheme;
}
```

If a CDN sits in front of the proxy, make the proxy trust that CDN's addresses and take the
visitor's address from the header the CDN sets, so that the first value is still one a visitor
could not choose.

Cached server-rendered responses (see [Caching](/docs/guides/caching)) live in the server's
memory on this target, one copy per process. Behind a load balancer every instance fills its own;
put a CDN in front if they should share one.

## Platforms

- **Fly.io, Railway, Render**: point them at the Dockerfile; set the port to 4321.
- **Kubernetes**: use the health check path `/api/health` for liveness and readiness probes.
- **Bare VPS**: run with a process manager such as `systemd` or `pm2`, and keep Node 24 current.

## Static hosting only

If you remove authentication and every `prerender = false` route, the site becomes fully static.
Set `output: 'static'` (already the default), delete the adapter and upload `dist/` to any static
host.
