## Unit and component tests (Vitest)

`vitest.config.ts` uses Astro's `getViteConfig()` so tests see the same aliases, plugins and
virtual modules as the application. Tests live next to the code as `*.test.ts(x)` or under
`tests/unit`.

```bash
pnpm test           # run once
pnpm test:watch     # watch mode
pnpm test:coverage  # V8 coverage report in ./coverage, checked against the floors below
```

Coverage is enforced, not only measured. `vitest.config.ts` sets floors per group of files:
the library code in `src/lib`, the build-time helpers in `config` and the React islands. A pull
request that drops a group below its floor fails the `unit` job. The floors sit a few points
under the current numbers, so they catch a regression without forcing tests for their own sake;
raise one when a group has settled above it. Files that only a running server exercises (pages,
actions, the middleware, the Better Auth wiring, the feed) are left out of the unit report and
covered by the Playwright suite instead.

Three styles are used in the template:

- **Plain unit tests** for helpers (`src/lib/*.test.ts`, `config/*.test.ts`).
- **Astro components** rendered with the Container API in the default Node environment
  (`tests/unit/components.test.ts`):

  ```ts
  import { experimental_AstroContainer as AstroContainer } from 'astro/container';
  const container = await AstroContainer.create();
  const html = await container.renderToString(Button, {
    props: { href: '/docs' },
    slots: { default: 'Docs' },
  });
  ```

- **React islands** with Testing Library in a DOM environment, opted in per file with
  `// @vitest-environment happy-dom`. Virtual modules such as `astro:actions` and the auth client
  are mocked with `vi.mock()`.

## End-to-end tests (Playwright)

The e2e suite runs against the production build of the Node target with an isolated SQLite
database that is recreated before every run.

```bash
pnpm build:node
pnpm test:e2e            # all projects (desktop Chromium + mobile emulation)
pnpm test:a11y           # only the axe accessibility checks
pnpm test:e2e:ui         # Playwright UI mode
```

Specs in `tests/e2e` cover the home page and dark mode, docs navigation, blog listing and tags,
search, SEO endpoints and metadata, the contact form (including the honeypot), the newsletter
(double opt-in, unsubscribe, the signed provider webhook), sign-up, sign-in and sign-out,
two-factor authentication, account export and deletion, the admin area (inbox, roles,
last-admin protection, health details), route caching, the back-to-top button, the single-locale
output, the design-system components, security headers, CSP violations and accessibility.

<Callout type="tip" title="Waiting for islands">
  Interactive React islands hydrate asynchronously. Use the `waitForIslands(page)` helper before
  clicking into a `client:visible` or `client:load` component to avoid flaky tests.
</Callout>

Set `PLAYWRIGHT_CHROMIUM_EXECUTABLE` to use a preinstalled browser instead of the one Playwright
downloads. `E2E_PORT` moves the test server off 4321, and `E2E_BASE_URL` points the suite at a
server that is already running (tests that read the local database skip themselves). Every
sign-up in the suite asks Have I Been Pwned whether the password is known, so the suite needs
network access to `api.pwnedpasswords.com`; `PASSWORD_BREACH_CHECK=false pnpm test:e2e` runs it
offline and skips the one test that checks the breach rule.

## Accessibility

`tests/e2e/a11y.spec.ts` runs [axe](https://github.com/dequelabs/axe-core) with the WCAG 2.1 AA
rule set and fails on any violation. It scans the public pages (home, docs, blog, changelog,
legal, contact, newsletter, search, the auth pages including the two-factor step and the 404
page), interactive states (the open mobile navigation, the open command
palette with results, the contact form with validation errors, a failed sign-in) and, signed in
once as an administrator, the dashboard with the account-deletion form open, the admin overview,
inbox, message detail, users, subscribers and audit log pages, including the inbox at phone
width. Components also follow the basics: visible focus rings, `aria-current` for
navigation, labelled dialogs, keyboard-navigable tabs and skip links.

## Lighthouse

Lighthouse runs against the built Node server in CI, three times per URL, and asserts on the
median run. Two configurations cover the two shapes of visitor:

- `lighthouserc.json` (desktop): the home page, a docs page, a blog post, the pricing table
  page (an interactive island), the search page (Pagefind and its WebAssembly) and `/login`
  (a server-rendered route with an auth island).
- `lighthouserc.mobile.json` (Lighthouse's default mobile emulation with CPU and network
  throttling): the home page, a docs page and a blog post.

Both configurations start the built Node server behind `scripts/lhci-server.mjs`, a small proxy
that gzips text responses. The standalone Node server serves HTML, CSS and scripts uncompressed,
while every supported deployment compresses them (the CDN on Vercel, Netlify and Cloudflare, the
reverse proxy in front of Node), and auditing the raw server scored the mobile pages about ten
points below what visitors see, enough to make the floors depend on the runner's speed.

Performance, accessibility, best practices and SEO all block below their floors; a performance
regression fails the pull request instead of printing a warning. Locally:

```bash
pnpm build:node
pnpm lhci            # both configurations
pnpm lhci:mobile     # one of them
```

Each run uploads its reports to Lighthouse's temporary public storage and prints the links.
