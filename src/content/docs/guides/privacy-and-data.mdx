The template is designed so the promises in the privacy policy are backed by real
functionality. This page lists what is stored, how people exercise their rights, and what you
must adapt before launch.

## What is stored where

| Data                                       | Table                   | Lifecycle                                                                                                     |
| ------------------------------------------ | ----------------------- | ------------------------------------------------------------------------------------------------------------- |
| Profile, verification, role                | `user`                  | Until the account is deleted                                                                                  |
| Password hash / OAuth links                | `account`               | With the user                                                                                                 |
| Sessions (IP, user agent)                  | `session`               | With the user; expired rows are removed by Better Auth                                                        |
| Two-factor secret and backup codes         | `two_factor`            | Encrypted with `BETTER_AUTH_SECRET`; with the user, or when 2FA is turned off or reset by an administrator    |
| Contact messages                           | `contact_message`       | Archived ones are pruned; open ones too if a maximum age is set (see below)                                   |
| Newsletter subscribers                     | `newsletter_subscriber` | Confirmed ones until they unsubscribe; pending and unsubscribed rows pruned after `NEWSLETTER_RETENTION_DAYS` |
| Throttle counters (keyed hash of IP/email) | `throttle`              | Expire after 15 minutes / 1 hour, pruned by `db:prune`                                                        |
| Audit log                                  | `audit_log`             | Kept indefinitely; contains no message bodies or secrets                                                      |

## Self-service

From the dashboard a signed-in user can:

- **Export** their data: `src/pages/api/account/export.ts` (POST, from the dashboard's form)
  returns profile, sign-in methods, sessions and, when the address is verified, contact messages
  from that address and the state of its newsletter subscription. Tokens and hashes are never
  included, and a GET answers 405 so a prefetched link can never record an export.
- **Delete** their account through Better Auth's `deleteUser`. Password accounts confirm with
  the password; social-only accounts need a fresh session (younger than a day). The
  `beforeDelete` hook in `src/lib/auth.ts` refuses to remove the last administrator, and
  `afterDelete` removes contact messages from a verified address and records the deletion in
  the audit log.
- **Change** their password, which signs out other sessions, and their name and avatar
  (rectification) from the profile form.

## Requests from people without an account

The contact form is the fallback. Messages arrive in the [admin inbox](/docs/guides/admin);
administrators can find everything tied to an address there, in the users page and in the
subscribers page, act on it and archive the request. The audit log shows what was done and when.

Newsletter subscribers manage themselves: the unsubscribe link in every email ends the
subscription, and the address is deleted by the retention job shortly after. See the
[newsletter form](/docs/components/newsletter-form#data-and-retention).

## Retention

`pnpm db:prune` deletes archived contact messages older than `CONTACT_RETENTION_DAYS` (default 365) and expired throttle counters. The **Prune data** workflow (`.github/workflows/prune.yml`)
runs it every Sunday at 03:00 UTC, and on demand from the Actions tab, against the database in
the repository's Actions secrets, the same ones the
[migration workflow](/docs/guides/ci-cd#database-migrations) reads. To change the defaults, add
`CONTACT_RETENTION_DAYS` and `CONTACT_MAX_AGE_DAYS` as repository _variables_ (Settings →
Secrets and variables → Actions → Variables).

By default open (new or read) messages are never deleted automatically, so
`CONTACT_RETENTION_DAYS` is not a maximum age for all contact data. If your policy needs one,
set `CONTACT_MAX_AGE_DAYS` as well: the same job then deletes every message older than that,
whatever its status, and says so in its output. Both values belong in the privacy policy.

The same job deletes newsletter addresses that were never confirmed or that unsubscribed more
than `NEWSLETTER_RETENTION_DAYS` (default 7) ago. Confirmed subscribers are kept until they
unsubscribe or an administrator removes them.

The audit log records message status changes and deletions together with the change (one
transaction); entries for everything else are best-effort. See the
[admin area](/docs/guides/admin#audit-log) before promising more than that in your policy.

## Launch checklist

1. Edit `src/content/legal/privacy.md` and `terms.md`: legal entity, contact address,
   jurisdiction, and the providers you actually use (hosting, Turso, Resend, OAuth, analytics).
2. Set `CONTACT_RETENTION_DAYS` (and `CONTACT_MAX_AGE_DAYS` if open messages must expire) and
   `NEWSLETTER_RETENTION_DAYS` to match the policy; the **Prune data** workflow runs
   `pnpm db:prune` weekly once the database secrets are in place.
3. Decide who the administrators are (`ADMIN_EMAILS`) and make sure at least one exists. The
   application refuses to remove the last one.
4. Configure `RESEND_API_KEY` so verification, resets, magic links and newsletter confirmations
   work, or accept that those features stay hidden. Set `newsletter.enabled` to `false` in
   `src/site.config.ts` if you do not want a newsletter at all.
5. Document your hosting provider's log retention in the policy.
6. Update `public/.well-known/security.txt` and `SECURITY.md` with real contacts.
