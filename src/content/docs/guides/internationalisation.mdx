The site renders in one language, English. Release 0.20.0 shipped a German layout (the chrome, the
home page, the about page and one blog post) and 0.21.0 took it out again: with the documentation,
the dashboard and the admin area in English, most links from a German page led back to English, and
a browser's built-in translation did a better job than a site that is translated in patches. What
stayed is the plumbing, configured for one locale, so that a project built on the template can add a
language without redoing the layout.

## What is in place

`astro.config.ts` enables [Astro's i18n routing](https://docs.astro.build/en/guides/internationalization/)
with the values from `src/i18n/config.ts`:

```ts
i18n: {
  defaultLocale,
  locales: [...locales],
  routing: { prefixDefaultLocale: false },
},
```

The default locale has no prefix, every other locale lives under its code (`/<locale>/blog`), and
there is **no fallback**: a page exists in a locale only when it has been translated. With one
locale configured, `/de` is a 404 and nothing in the markup mentions another language.

Every component of the chrome reads its strings through `useTranslations()` rather than writing
them inline:

```astro
---
import { resolveLocale, useTranslations } from '@/i18n';

const locale = resolveLocale(Astro.currentLocale);
const t = useTranslations(locale);
---

<a href="#main">{t('skip')}</a>
```

`src/i18n/ui.ts` holds those strings. English is the reference: its keys define the set, and the
type of every other dictionary makes each key mandatory, so a missing translation is a type error
and a unit test checks that no value is empty. Placeholders in braces are filled by `t()`:

```ts
t('footer.copyright', { year: 2026, author: 'Ada' });
// © 2026 Ada. Released under the MIT License.
```

Two more maps in the same file deal with `site.config.ts`, which stays English: `labels`
translates navigation and footer entries (keyed by `href` for links and by the English title for
footer groups), and `localizedRoutes` lists the English paths that have a translated page. Both
are empty while the site has one locale.

The rest of the plumbing is spread over the code that renders content:

- `src/components/pages/HomePage.astro` renders the home page from one copy object per locale
  (`src/i18n/pages/home.ts`), so a translated home page is a second object and a one-line page.
- `src/components/pages/BlogIndex.astro` renders the blog for a locale and can list the English
  posts a locale still lacks; `PostCard.astro` marks a post written in another language.
- `src/lib/content.ts` reads a post's locale from its folder (`postLocale`, `postSlug`) and finds
  translations by slug (`postAlternates`, `untranslatedPosts`); `src/lib/docs.ts` does the same for
  the docs collection (`buildDocsTree(entries, locale)`), and `src/lib/rss.ts` builds the feed for
  a locale.
- `Head.astro` turns the `alternates` a page passes to `BaseLayout` into
  `<link rel="alternate" hreflang="…">` for every language version, an `x-default` for the English
  page and `og:locale:alternate`. With one locale it emits none of them.
- Dates use `formatDate(date, options, intlLocales[locale])`; Pagefind indexes each language from
  the page's `lang` attribute, so a palette on a translated page would search that language only.

## Adding a locale

<Steps>

1. **Configure it.** Add the code to `locales` in `src/i18n/config.ts`, with its native name,
   `Intl` tag and Open Graph value. TypeScript now lists every dictionary and map that lacks it.
2. **Translate the chrome.** Add a dictionary to `ui.ts`, plus `labels` entries for the navigation
   and footer and a `localizedRoutes` entry for each page you translate. Links from the header and
   footer go to the translation when there is one and to the English page otherwise.
3. **Add the pages** under `src/pages/<locale>/`: an `index.astro` that renders `HomePage` with the
   locale and a copy object in `home.ts`; `about.astro` as prose; `blog/[...page].astro` and
   `blog/[slug].astro` that call `getPublishedPosts(locale)` and pass `postAlternates()`; an
   `rss.xml.ts` that calls `buildFeed(context, locale)`. Pass `alternates={alternatesFor('/…')}`
   to `BaseLayout` on each translated chrome page so the `hreflang` links appear.
4. **Translate posts** by putting a file with the same slug under `src/content/blog/<locale>/`.
5. **Offer the switch.** A language switcher is a small `<nav>` that maps `otherLocales(locale)` to
   `alternates[other] ?? localizeHref('/', other)`; place it in `Header.astro` and `MobileNav.astro`
   and pass the layout's `alternates` down to it.
6. **Test it.** Extend `tests/e2e/i18n.spec.ts` (today it asserts the single-locale output) and the
   page lists in `a11y.spec.ts` and `security.spec.ts` with the new pages.

</Steps>

## What to leave in English, at least at first

- **Documentation.** Translating forty pages is a project of its own, and a partially translated
  manual is worse than an English one. The docs collection supports a `<locale>/` folder when you
  get there.
- **Account, admin and auth pages, actions and emails.** They are rendered on demand for one person
  and their strings live in the components and in `src/lib`; translate them the same way when your
  product needs it.
- **`site.config.ts`.** Names, URLs and the English labels; translations layer on top through
  `labels`.

## Testing

`src/i18n/index.test.ts` covers the path helpers, the dictionaries and the label maps, and pins
down the single-locale behaviour: no alternates, no other locales, an unconfigured prefix treated as
an ordinary path. `src/lib/content.test.ts` and `src/lib/docs.test.ts` do the same for the content
helpers. `tests/e2e/i18n.spec.ts` checks that pages declare `lang="en"`, emit no `hreflang` links
and no language navigation, and that `/de` is a 404.
