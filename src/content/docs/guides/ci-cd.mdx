## Pull request checks

`.github/workflows/ci.yml` runs on pushes to `main` and on every pull request. Each job checks
out the repository and runs the composite action in `.github/actions/setup` (pnpm, Node from
`.nvmrc`, `pnpm install --frozen-lockfile`) before its own steps:

| Job          | What it runs                                                                                                               |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- |
| `quality`    | `pnpm lint`, `pnpm format:check`, `pnpm check`, `pnpm audit --audit-level=high`                                            |
| `unit`       | `pnpm test:coverage`, failing under the coverage floors, report as an artifact                                             |
| `build`      | `pnpm build:<target>` for each of `node`, `vercel`, `netlify` and `cloudflare`                                             |
| `e2e`        | `pnpm build:node` then `pnpm test:e2e` with a cached Playwright Chromium; a test that passes only on a retry fails the job |
| `lighthouse` | `pnpm lhci` against the Node build: desktop and mobile, three runs, blocking                                               |

The matrix is the guarantee behind "deploy anywhere": a dependency that only works on one
runtime fails the pull request instead of a production deploy.

### How the test servers are started

The `e2e` and `lighthouse` jobs start the built Node server on `127.0.0.1` explicitly
(`HOST=127.0.0.1`) instead of the adapter's default `localhost`, which resolves to IPv6 first on
GitHub's runners while the tests connect over IPv4. The browser in the Playwright suite still
visits the server as `http://localhost:4321`, because WebAuthn needs a hostname as the relying
party and refuses an IP address (`tests/e2e/passkeys.spec.ts`); Chrome and Node fall back to IPv4
for `localhost` on their own. The Playwright web-server command also resets
and migrates `.data/e2e.db` before the server starts (Playwright launches the web server before
`globalSetup`), and the tracked `.data/.gitkeep` keeps that directory present on a fresh checkout.
The Lighthouse job puts the server behind `scripts/lhci-server.mjs`, a gzip proxy, so the audit
measures compressed responses the way every deployment serves them.

### Audit exceptions

`pnpm audit --audit-level=high` fails the `quality` job on new high or critical advisories.
`pnpm-workspace.yaml` handles the transitive advisories the template cannot upgrade directly:

- `overrides` pins patchable transitive packages to a fixed version. Currently `fflate` inside
  the Open Graph image generator (Satori pins a version with a ZIP parsing flaw), `path-to-regexp`,
  `sharp`, `undici` inside Cloudflare's local emulator (miniflare pins a release with a
  WebSocket decompression flaw) and `devalue`, Astro's serializer for action results, moved to the
  release that fixes two unhandled-rejection advisories.
- `auditConfig.ignoreGhsas` lists advisories with no upstream fix in build-time tooling that never
  runs on the deployed site: two for `extract-zip` inside the Netlify adapter's development tooling
  (GHSA-jmr9-qjv8-65gv, GHSA-7pqw-9j4j-h8q3), one for the esbuild 0.18 that drizzle-kit's
  config loader pins (GHSA-67mh-4wv8-2f99, a flaw in esbuild's development server), two in the
  same Netlify tooling for `node-forge` inside `listhen`, its local HTTPS development server
  (GHSA-86w9-cpqp-85rv, an RSA signature verification flaw) and `braces` inside its function
  bundler's glob matcher (GHSA-vfj7-8cjw-p6xm, stack exhaustion on a crafted pattern), and one
  for `http-cache-semantics`, the cache policy Astro applies to assets it fetches at build time
  (GHSA-ch52-4w7c-c8xp, about a shared HTTP cache serving several users, which a build is not).
  None of these has a patched release.

Review both lists when upgrading dependencies: drop an entry once the package has moved past the
advisory, and check that a plain `pnpm audit` reports nothing.

## Dependency updates

`.github/dependabot.yml` opens grouped pull requests every Monday: Astro packages, React and
Motion, auth and data (Better Auth, Drizzle, libSQL, Resend), styling, tooling, and the GitHub
Actions used by the workflows and the composite action. Because the CI matrix builds every
target, merging an update is safe when the checks are green.

Two dependencies are held back on purpose: TypeScript stays on the 6.x line (`~6.0.3`) because
`@astrojs/check` and `typescript-eslint` do not yet support TypeScript 7, and `@types/node` follows
the Node 24 runtime pinned in `engines` and `.nvmrc`. Both are listed under `ignore`.

Newly published versions wait three days before Dependabot proposes them (`cooldown`). Dependabot
passes the same gate to pnpm while it rewrites the lockfile; pnpm 12 applies it only to the
packages being updated and keeps the versions already pinned in `pnpm-lock.yaml`. (pnpm 10 and 11
re-checked every lockfile entry, which made updates fail whenever any package was younger than
three days.) Locally, pnpm waits one day before resolving a newly published version
(`minimumReleaseAge`); `pnpm install` from the committed lockfile is unaffected.

## Releases with Changesets

<Steps>

1. When a change is user-facing, add a changeset with the pull request:

   ```bash
   pnpm changeset
   ```

2. Merge the pull request. `.github/workflows/release.yml` opens (or updates) a
   **chore: version packages** pull request that bumps `package.json`, rewrites `CHANGELOG.md`
   and deletes the consumed changesets. The repository setting "Allow GitHub Actions to create
   and approve pull requests" must be on for this.

3. Merge the version pull request. The workflow tags the release, and the next deploy renders
   the new entry on `/changelog`.

</Steps>

The built-in `GITHUB_TOKEN` cannot trigger other workflows, so a version pull request opened
with it has no CI run: GitHub records a run that never starts and closes it as failed when the
branch is deleted. To have CI, CodeQL and the branch rules apply to that pull request as well,
create a fine-grained personal access token limited to the repository with **Contents** and
**Pull requests** set to read and write, and store it as the `RELEASE_TOKEN` Actions secret. The
workflow uses it when present and falls back to `GITHUB_TOKEN` otherwise. Fine-grained tokens
expire after a year at most; when yours does, the fallback quietly returns and the version pull
request loses its checks again, so note the renewal date.

The site is a private package, so nothing is published to npm; `privatePackages.tag` in
`.changeset/config.json` still creates Git tags.

## Database migrations

`.github/workflows/migrate.yml` applies the migrations in `drizzle/` to the production database
with `pnpm db:migrate`. Run it from the Actions tab after the first deployment and whenever you
want to apply pending migrations; it also runs automatically when a push to `main` adds or edits
a file under `drizzle/`. It reads the database URL and token from GitHub Actions secrets named
`DATABASE_URL` and `DATABASE_AUTH_TOKEN` or `TURSO_DATABASE_URL` and `TURSO_AUTH_TOKEN`, as
repository secrets or as secrets of the `production` environment the job references (add a
required-reviewer rule there if you want approvals). The first step logs which of the four
names are present, and the job refuses a `file:` URL.

The [operating guide](/docs/guides/operations) lists this and the other recurring jobs in one
table.

## Data retention

`.github/workflows/prune.yml` runs `pnpm db:prune` every Sunday at 03:00 UTC and on demand. It
reads the same database secrets as the migration workflow plus the optional
`CONTACT_RETENTION_DAYS`, `CONTACT_MAX_AGE_DAYS` and `NEWSLETTER_RETENTION_DAYS` repository
variables (see
[privacy and data](/docs/guides/privacy-and-data#retention)). If the newsletter mirrors
subscribers to a Resend audience, add `RESEND_API_KEY` and `RESEND_AUDIENCE_ID` (a secret or a
variable) as well: the job retries the audience syncs that failed before it prunes, and keeps
an opt-out the provider has not received. Check its runs now and then: a retention policy is
only real while the job succeeds.

## Deploy previews

Vercel and Netlify build every pull request automatically. Preview URLs are added to Better
Auth's trusted origins at runtime (see `src/lib/env.ts`), so sign-in works on previews without
extra configuration.

## Local pre-commit hook

Husky runs `lint-staged` before every commit: ESLint with autofix and Prettier on staged files.
Skip it in an emergency with `git commit --no-verify`.
